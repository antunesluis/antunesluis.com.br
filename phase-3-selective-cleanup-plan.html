Resumo da análise

Há trabalho real, mas ele é menor que uma refatoração arquitetural

A arquitetura por features está clara e os fluxos essenciais já têm boa cobertura. A Fase 3 deve concentrar-se em cinco núcleos: contratos de Server Actions, tipagem de dados estruturados, remoção dos repositórios JSON sem uso, simplificação transacional do seed e centralização local das tags de cache. Não há justificativa para base repositories, fábricas de CRUD, uma camada de casos de uso ou migração para Cache Components.

Arquivos de teste 20

Vitest em modo determinístico e serial.

Testes aprovados 103

Incluem CRUD, autenticação, upload, seed e repositórios.

Usos explícitos de any 3

Dois no repositório de projetos e um em JSON-LD.

Lint atual 0 erros / 3 avisos

Dois imports mortos e uma navegação interna inadequada.

Problemas reais que justificam alteração

  • CRUD JSON sem consumidores e seed de posts comentado desde 2025.
  • Contratos de retorno divergentes entre ações e mensagens em dois idiomas.
  • any escondendo a conversão de techStack e a diferença entre null e undefined.
  • Seed escrevendo tabelas diretamente e sem transação entre limpeza e inserção.
  • Tags literais repetidas em consultas e mutações de cada feature.
  • JSON-LD duplicado, imports mortos, copy de projeto dizendo “Post” e TODO concluído.

Pontos já adequados

  • Blog e projetos não importam um ao outro.
  • Componentes e ações consomem repositórios, não consultas Drizzle.
  • O repositório Drizzle de posts já é tipado sem any.
  • As mutações verificam autenticação antes de ler entrada ou causar efeitos.
  • A invalidação atual cobre lista e detalhe conforme create, update e delete.
  • Testes usam SQLite isolado e a linha de base de testes e build está verde.
Decisão central: preservar as classes de repositório Drizzle como fronteira de persistência, mas remover interfaces que só existem para implementações JSON mortas. “Usar repositórios” não exige uma interface sem segunda implementação.

Mapear duplicação entre blog e projetos Aplica Os pares create, update e delete têm 43 a 90 linhas e a mesma sequência de autenticação, validação, repositório, cache e retorno. Queries, formulários e botões também são paralelos. Compartilhar apenas o contrato mínimo de resultado. Manter ações, queries, formulários, botões e repositórios dentro de cada feature.
Padronizar resultados e idioma das Server Actions Aplica Create e update usam errors[] e success?; delete, login e upload usam error. As ações CRUD misturam “Dados inválidos” e “Unknown error”. O formulário de projetos anuncia “Post updated”. Adotar success: boolean e errors: string[] somente no CRUD de blog e projetos, onde há consumidores equivalentes. Preservar os contratos específicos de login e upload. Usar inglês nas mensagens CRUD do painel.
Substituir any Aplica drizzle-project-repository.ts possui dois any com suppressions. JsonLd.tsx usa Record<string, any> e tem exceção dedicada no ESLint. Usar os tipos select/insert do schema Drizzle, o modo JSON tipado para techStack e os tipos do schema-dts, dependência já instalada e hoje sem uso.
Revisar repositórios JSON Aplica JsonPostRepository tem zero consumidores. JsonProjectRepository só é instanciado pelo seed, que chama apenas findAll(); os demais métodos são mortos. posts.json também não é lido. Remover os dois repositórios JSON, seus contratos artificiais e o fixture de posts sem consumidor. Manter somente projects.json, importado diretamente pelo seed.
Simplificar seed sem quebrar a fronteira Aplica seed.ts importa tabela Drizzle, apaga tudo e só depois insere. Uma falha de insert pode deixar a tabela vazia. Há 12 linhas comentadas de seed de posts. Executar delete + insert em uma transação no próprio script de infraestrutura. O modo JSON tipado elimina a serialização duplicada, sem adicionar uma API de repository usada apenas pelo seed.
Centralizar tags somente com duplicação real Aplica blog, blog-${slug}, projects e project-${slug} se repetem em queries, create, update, delete e expectativas de integração. Criar nomes e funções de detalhe dentro de cada feature. Não criar um registrador global ou helper genérico de cache.
Auditar APIs de cache sem migrar preventivamente Adequado next.config.ts não habilita cacheComponents. As consultas públicas usam unstable_cache; mutações usam updateTag dentro de Server Actions. Manter a estratégia. No modelo sem Cache Components, a documentação do Next.js 16 ainda descreve unstable_cache para funções que consultam banco. updateTag oferece leitura após escrita.
Extrair casos de uso somente com justificativa Não aplica Cada operação mutável tem um único ponto de entrada. Não há regra reutilizada por múltiplos chamadores, orquestração externa ou vários efeitos independentes que exijam teste isolado. Não criar diretório de use cases, services, ports ou factories. As Server Actions continuam coordenando autenticação, validação, repositório, cache e navegação.

Escopo confirmado

Alterações que têm evidência e consumidor

1. Contratos e feedback das ações

Um contrato-base pequeno para success e errors, usado apenas pelo CRUD de blog e projetos. Login e upload preservam seus contratos específicos.

2. Persistência tipada de projetos

Usar JSON tipado do Drizzle para techStack, normalizar deployUrl na fronteira e eliminar os dois any sem acoplar componentes ao formato SQLite.

3. JSON e seed

Eliminar implementações completas sem consumidor, manter somente o fixture de projetos e tornar a substituição do seed atômica dentro do módulo de repositório.

4. Cache local por feature

Centralizar apenas os valores repetidos. O mecanismo de cache, os limites e a semântica de invalidação permanecem iguais.

5. Dados estruturados

Consumir schema-dts, hoje instalado e ocioso, tipar os schemas JSON-LD e remover a exceção de lint para any.

6. Limpeza localizada

Remover imports mortos, JSON-LD duplicado, fallback legado de techStack, TODO concluído e copies incorretas, além de corrigir a navegação que gera warning no lint.

Itens explicitamente fora de escopo

Não implementar nesta fase:
  • base repository, repository genérico ou interfaces preventivas;
  • fábrica genérica de CRUD ou helper que execute Server Actions;
  • componente genérico para formulários ou exclusão;
  • camada de casos de uso, services, ports ou adapters adicionais;
  • Cache Components, use cache, política de TTL ou troca do mecanismo de cache;
  • mudança de UI, Base UI, upload seguro ou otimização de imagens;
  • alteração de schema físico, migração de banco ou mudança de conteúdo;
  • refatoração ampla de SEO, busca ou componentes client além dos avisos e duplicações concretos;
  • documentos PRD/PLAN/tasks ou qualquer recriação do workflow agentic antigo.

Persistência

Tipar a fronteira Drizzle de projetos

Problema encontrado

Dois any silenciam o formato real da linha SQLite. techStack é um JSON string no banco e array no modelo. deployUrl pode voltar como null, embora o modelo exponha campo opcional.

Arquivos e áreas

  • src/db/drizzle/schemas.ts
  • src/features/projects/repositories/drizzle-project-repository.ts
  • src/features/projects/repositories/drizzle-project-repository.test.ts

Alterações propostas

  • Declarar techStack como texto em modo JSON com $type<string[]>(); a coluna física continua TEXT.
  • Usar tipos inferidos de select e insert nas conversões.
  • Normalizar null de deployUrl para a representação do modelo na fronteira.
  • Remover suppressions e o fallback de array/string que não possui consumidor tipado.

Riscos e validações

  • Risco: alterar serialização de registros existentes.
  • Testar leitura de JSON já persistido, create, update, delete e projeto sem deployUrl.
  • Confirmar que Drizzle lê e grava a mesma representação TEXT sem gerar migração física.
2

Legado e seed

Remover repositórios JSON mortos e tornar o seed atômico

Problema encontrado

Uma implementação JSON inteira não tem consumidor; a outra expõe CRUD, mas o seed usa apenas leitura. As interfaces só justificam essas duas implementações. O seed apaga antes de inserir sem transação e acessa Drizzle diretamente.

Arquivos e áreas

  • src/features/blog/repositories/json-post-repository.ts e post-repository.ts
  • src/features/projects/repositories/json-project-repository.ts e project-repository.ts
  • Índices e repositórios Drizzle das duas features
  • src/db/drizzle/seed.ts, seed.integration.test.ts
  • src/db/seed/posts.json e projects.json

Alterações propostas

  • Excluir as duas classes JSON, as duas interfaces de implementação única e o fixture de posts sem leitor.
  • Manter projects.json como dado de seed e importá-lo diretamente.
  • Executar a substituição em uma transação local ao script de seed, sem ampliar a API do repository.
  • Remover o bloco comentado de posts e a serialização duplicada do script.
  • Preservar logs de sucesso, propagação de falha e código de saída não zero.

Riscos e validações

  • Risco: exclusão de fixture histórico de posts. Ele permanece recuperável pelo Git e deve ser removido somente após uma última busca de consumidores.
  • Testar seed isolado, contagem e conteúdo, execução repetida, ausência da tabela e rollback quando a inserção falhar.
  • Executar o CRUD dos dois repositórios após remover as interfaces.
3

Server Actions

Padronizar resultado e feedback sem criar executor genérico

Problema encontrado

O painel precisa interpretar error, errors e ausência de success. As mensagens CRUD alternam português e inglês. Projetos exibem mensagens de sucesso de posts.

Arquivos e áreas

  • Novo tipo compartilhado em src/lib/
  • Ações de blog e projetos
  • Formulários e botões de exclusão de blog e projetos
  • Testes unitários e de integração dessas ações

Alterações propostas

  • Definir apenas a base { success: boolean; errors: string[] }.
  • Compor o estado de formulário do CRUD sem um DTO genérico de dados.
  • Não alterar os contratos de login e upload, pois seus consumidores têm necessidades diferentes.
  • Manter logout e redirects como exceções naturais, pois sucesso encerra a ação.
  • Usar inglês em feedback e validação do painel e corrigir “Post” no formulário de projetos.
  • Não extrair autenticação, parsing, try/catch ou execução do repositório para helpers.

Riscos e validações

  • Risco: quebrar consumidores client por mudança de shape.
  • Atualizar primeiro as expectativas de contrato e depois os consumidores.
  • Executar testes de autenticação sem efeitos, ciclos CRUD e upload; fazer smoke manual de create, update, delete, login e upload.
4

Cache

Centralizar tags dentro de cada feature

Problema encontrado

Lista e detalhe dependem de strings repetidas entre as queries e três ações por feature. Um typo futuro pode invalidar uma tag diferente daquela atribuída à consulta.

Arquivos e áreas

  • Novos módulos de tags em features/blog/lib/ e features/projects/lib/
  • Queries públicas e seis ações CRUD
  • Testes de integração dos CRUDs

Alterações propostas

  • Definir a tag de lista e uma função de tag por slug em cada feature.
  • Consumir os mesmos símbolos na criação do cache e na invalidação.
  • Preservar exatamente: create invalida lista; update e delete invalidam lista e detalhe.
  • Manter unstable_cache, React cache e updateTag.

Riscos e validações

  • Risco: alterar uma string quebra invalidação sem erro de tipo.
  • Manter os valores externos atuais e as expectativas exatas nos testes de integração.
  • Smoke manual: criar, editar, despublicar e excluir, verificando lista pública, detalhe e painel.
